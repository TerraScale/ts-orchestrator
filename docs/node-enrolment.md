# Node identity and enrolment

Each host creates its identity before starting host services. Private keys stay
at /var/lib/ts-orch/node/tls.key (PKCS#8 P-256) and node/wg.key (base64
X25519). The daemon creates root-owned 0600 files in a root-owned 0700 node
directory. Existing files with a wrong owner or mode, damaged keys, and
incomplete pairs are reported and left unchanged. The host keeps serving and
receiving releases. Both keys are generated only when neither exists.
The public-key command reads an existing pair without creating one.

These keys are independent of the release listener's identity. Nothing yet
uses the node list to change mesh membership, release delivery or regional
host pinning.

## Add or remove a host

Read each host's public identity through the authenticated operator SSH path:

    ssh NODE 'sudo ts-orch node keys' > NODE-public.json

An optional positional STATE directory selects another local state directory.
Only wg_public_key and tls_spki_sha256 appear in that output. Never collect
private key files. Add the public identity, name, region and addresses to
an inventory array, then build the repository list:

    ts-orch node list build "$sequence" inventory.json deploy/m1/nodes.json
    make generate
    ts-orch node list check deploy/m1/nodes.json

The last command runs the validation every host applies before adopting a list.
`make generate-check` runs it in CI, so a list that hosts would refuse fails
the pull request.

Names use exactly ts-<lowercase catalog region>-<index>, with indices 1 through
254 and no leading zeroes. mesh_ip is derived as
10.201.<fixed catalog mesh index>.<node index>. Consult
[the address plan](network/address-plan.md) before adding routes.

Every entry has name, region, public_ip, private_ip, mesh_ip, wg_public_key and
tls_spki_sha256. Keys must have their exact canonical base64 or lowercase hex
encoding; even escaped CR/LF in base64 is refused. Uniqueness compares decoded
key bytes and parsed IPv4 addresses, including addresses across fields.
Names, keys and addresses must be unique and mesh addresses must match the
derived value.

Choose a sequence higher than the previous list, commit nodes.json and its
generated bytes in deploy/m1/embed.go, merge the PR, and release the agent.
To remove a host, remove its entry and follow the same sequence, build, merge
and release steps. Removing the last host is valid: a higher sequence with an
empty nodes array is adopted. The initial sequence-zero empty list represents
no enrolled hosts.

## Delivery and trust

The list travels only inside the agent binary. The existing release path
verifies that binary's digest against the signed run before executing it.
The embedded list has exactly the trust of the code running as root.
There is no separate list message, bearer-token envelope, raw-file download,
publication command or relay of lists between hosts.

Today a list change is authorised by whatever authorises a release of the
agent: a merge to main that passes CI. scripts/ci/node-list.py runs from the
pull request it checks. A PR can change both the list and that checker, so the
checker is a consistency guard, not an independent authorisation boundary.
It checks embedding, sequence increases and fixed catalog mesh indices.
This change introduces no second signer or additional approval requirement.

Adoption has one validation point before persistence. Owners can later add an
independent authorisation check there without creating another delivery path.

## Adoption and status

At every start the host loads its stored list. Once the release is confirmed,
after probation passes, it considers the embedded list. A release rolled back
before confirmation cannot change the stored list.

| Embedded versus stored | Result |
| --- | --- |
| Higher sequence, valid contents | Atomically persist and adopt |
| Equal sequence, identical contents | Keep the list without rewriting it |
| Equal sequence, different contents | Refuse; keep the stored list |
| Lower sequence | Silently keep the stored, higher list |
| Invalid embedded contents | Refuse; keep the stored list |

The list is stored in node/nodes.json under the host state directory.
Persistence uses an atomic rename and syncs both the file and its directory.
The stored sequence never goes backwards, including when an older binary is
restored. The digest is SHA-256 of the adopted list's JSON encoding, independent
of whitespace in the source file.

The three refusal cases are invalid embedded contents, conflicting contents at
the same sequence, and a stored-state or persistence error. Each is reported in
one log line and in status as "node list: refused, <reason>". Serving and release
confirmation continue. A damaged stored list is preserved for operator repair;
the host does not overwrite a sequence it cannot read.

The host's status reply includes node_list.sequence, node_list.digest and an
optional node_list.refused. ts-orch status prints the sequence and digest with
each region's health, or the local host's health without a mesh. The release
version reply also carries this data for individual hosts. Refusal keeps the
adopted list's sequence and digest visible and does not turn release health red.
A local status snapshot in node/list-status.json lets the CLI read the daemon's
decision without independently adopting its own embedded list.

The M1 node-list lane runs real daemons with distinct embedded lists, verifies
confirmation and rollback timing, restart monotonicity, refusals and status,
and checks that invalid identity files remain untouched while the host serves.
