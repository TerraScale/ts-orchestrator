# Continuous task readiness

After a one-minute start grace, a host probes its watched tasks concurrently in rounds, with a 15-second request deadline and at least ten seconds between observations of a task. A failing observation means that the request reached that exact task, was fully written, and received no first response byte before the deadline. It contributes to the five-minute failing window only when another watched task on this host answered in the same round; data owners also count as witnesses. When this is the host's only watched task, the same prober instead probes the agent's own loopback health endpoint in that round. A round without a witness is suspect and neither adds to nor resets the window; an endpoint lookup failure is also unobserved and neither adds nor resets it. In a witnessed round, an answered probe (including HTTP 503) or another observed error clears the window. Replacement requires five minutes of witnessed failure and no other replaceable task currently in a failing window on this host. Correlated failures are reported and retained. Across all services, each host can authorize at most one automatic replacement in any fifteen minutes; a denied task keeps its window and is reconsidered in later rounds. After an authorized replacement, preparation for that slot waits 1, 2, 4, 8, then 15 minutes after repeated readiness failures. Thirty minutes of successful witnessed observations clears this per-slot history.

Only tasks with a declared readiness endpoint and positively established absence of data ownership can be replaced: ordinary containers without mounts, including identity and dashboard services, and function workers without mounts. Databases, qualified or stateful members, tasks marked as TerraBase, and every task with a mount are retained. Unknown ownership, including an error while determining it, is treated as ownership. The original process is stopped before failure is reported to the scheduler. Readiness observer errors and deadlines never enter a qualified member's execution scope or lifecycle error path.

Every watched task has a `ts_orch_task_unresponsive_seconds{task,service}` gauge. For a retained unresponsive task it reports wall time since the first unanswered observation, including suspect rounds, once the five-minute reporting threshold is crossed. This reporting clock is separate from the witnessed time required for replacement. It returns to zero when a witnessed observation clears the predicate, and is removed when observation ends. Each retained episode logs one warning and one line when the window clears:

| Situation | Operator sees | Action |
| --- | --- | --- |
| Data owner | `not replaced: data owner`, duration gauge | Retained |
| Unknown ownership | `not replaced: ownership unknown`, duration gauge | Retained |
| No other task or local witness answered | `not replaced: no witness answered`, duration gauge | Retained; suspect rounds do not advance the window |
| Other replaceable tasks also have failing windows | `not replaced: correlated with <n> other tasks`, duration gauge | All retained while correlated |
| Host replacement budget used or cannot be established safely | `not replaced: host replacement budget unavailable`, duration gauge | Retained and reconsidered after the budget frees |
| Exact task endpoint cannot be established | `ts_orch_task_readiness_unobserved_total{task,service}` increments each skipped round; one `task readiness not observed: exact task endpoint unavailable` warning per watch | No observation; the shared service port is never substituted for a missing task port |

The budget is serialized and recorded next to the host runtime socket before a stop is authorized. Agent restarts retain it. An unreadable or invalid budget record blocks replacement. A task using a fixed host port by design is probed at that port; a task using `${PORT}` must have a readable, valid, nonzero port label identifying its own endpoint.

Decisions are local to a host. The same fault affecting several hosts can lead each host to replace one task. A task whose readiness handler hangs on a dependency for more than fifteen seconds while it still serves traffic can be replaced if it is the only failing task and witnesses keep answering. Services should bound their own readiness checks.

Readiness metrics are exported on the private orchestrator and host metrics listeners. An alert rule belongs to monitoring configuration.

Stopping and starting an agent leaves assigned task processes running. The lifecycle journey uses real cluster nodes and records surviving process IDs for correlated freezes and recovery, loss of all witnesses, retained data owners, an unreadable task port beside a frozen shared-port sibling, individual replacement, the real fifteen-minute host budget across two services, and agent stop/start. With the fixed product constants, this lane takes approximately 33 minutes; it does not shorten the window or budget.
