# NetBird in milestone 1

ts-orch runs TerraScale's self-hosted NetBird on `ts-gru-1` and enrolls every
TerraScale host as a peer. The operator PC joins with one command whose setup
key is read from OCI Vault on the PC.

## Public ports (OCI network thread opens these on ts-gru-1)

| Port | Proto | Source | Why |
|---|---|---|---|
| 443 | tcp | 0.0.0.0/0 | Edge TLS for `netbird.terrascale.tech`: management gRPC, signal gRPC, relay websocket, REST API, embedded IdP |
| 80 | tcp | 0.0.0.0/0 | ACME HTTP-01 for the edge certificate (already open) |
| 3478 | udp | 0.0.0.0/0 | STUN (NAT discovery), served directly by `netbird-server` |
| 51820 | udp | 0.0.0.0/0 | WireGuard on ts-gru-1's own client, so peers connect directly instead of through the relay |

Nothing else is public. SSH (22/tcp) is NetBird-only: delta, beta and
mariogk-dev reach `ts-gru-1`, `ts-sjc-1` and `ts-fra-1` by their NetBird IPs
(their `~/.ssh/config` aliases point there), and no NSG opens 22 to the
internet.

## Server

- Image: `docker.io/netbirdio/netbird-server:0.81.3@sha256:9b2f606efefa8ea176e2afbb35c79622ca318e2e605ff1a0f6cb7e158ac08336`
  (linux/arm64 manifest of the upstream combined server: management, signal, relay, STUN and the embedded
  IdP in one process).
- ts-orch service `netbird-server` (`deploy/m1/services/netbird-server.json`),
  host network, plain HTTP on `127.0.0.1:8095`, STUN on `0.0.0.0:3478/udp`,
  health on `127.0.0.1:9095`, metrics on 9096 (not public).
- State: `/var/lib/ts-data/netbird` (SQLite store, IdP keys, `config.yaml`).
- `exposedAddress` is `https://netbird.terrascale.tech:443`. ts-orch sets the
  peer range to `10.200.0.0/16` so it never overlaps Tailscale's
  `100.64.0.0/10` on the NixOS hosts.

### What the edge (W5) must do for `netbird.terrascale.tech`

One hostname, one backend `127.0.0.1:8095`. The backend multiplexes by request:

1. gRPC: HTTP/2 requests with `Content-Type: application/grpc*`. The edge must
   forward them as HTTP/2 cleartext (h2c) to the backend, keep trailers, and
   never time out or buffer the stream (management sync and signal streams
   stay open for hours).
2. Websockets: `/relay`, `/ws-proxy/management`, `/ws-proxy/signal` need
   `Upgrade` pass-through with no idle timeout.
3. `/api/*` and `/oauth2/*` are ordinary HTTP/1.1 or HTTP/2.
4. Other paths are the NetBird dashboard, served directly by the Go edge.
   `/nb-auth` and `/nb-silent-auth` serve the application entrypoint for OIDC.

A `httputil.ReverseProxy` with an `http2.Transport{AllowHTTP: true}` dial to
the backend (h2c) and `FlushInterval: -1` covers all three.

## Secrets (OCI Vault `gru-vault`, compartment `gru-1-control`, names only)

| Secret | Made by | Used by |
|---|---|---|
| `gru-1-netbird-relay-auth-secret` | generated by ts-orch | server `authSecret` |
| `gru-1-netbird-datastore-encryption-key` | generated by ts-orch | server `store.encryptionKey` |
| `gru-1-netbird-session-cookie-key` | generated by ts-orch | server `auth.sessionCookieEncryptionKey` |
| `gru-1-netbird-owner-password` | generated by ts-orch | owner `mariogk@terrascale.tech` in the embedded IdP |
| `gru-1-netbird-admin-pat` | ts-orch, first start (`/api/setup` over loopback) | ts-orch reconcile of groups, policies, setup keys |
| `gru-1-netbird-setup-key` | ts-orch (reusable, 90 days, auto-rotated, group `gru-servers`) | TerraScale server hosts |
| `gru-1-netbird-operators-setup-key` | ts-orch (reusable, 90 days, auto-rotated, group `operators`) | dev hosts and the operator PC |

ts-gru-1's instance principal creates and reads these, so its dynamic group
needs, in compartment `gru-1-control`: `manage secret-family where
target.secret.name = /gru-1-netbird-*/` and `use keys` on `gru-vault-master`.

## Runtime

- `ts-orch-netbird.service` (`deploy/m1/services/netbird-server.service`) runs
  `ts-orch netbird server`: creates the generated secrets once, writes
  `/var/lib/ts-data/netbird/config.yaml` (0600, container user), claims the
  owner, syncs groups and policies (`manager.GRU()`), stores the setup keys,
  and enrolls ts-gru-1's own NetBird client. It repeats every 10 minutes.
- The install script installs the upstream `netbird` client package on
  ts-gru-1 and that unit; `ts-orch service apply -f
  deploy/m1/services/netbird-server.json` starts the server.

## Security notes

- The edge answers 403 to `/api/setup` on `netbird.terrascale.tech`; only
  ts-orch claims the owner, over loopback.
- The admin PAT and both setup keys live 90 days. Each 10-minute loop makes
  a successor within 30 days of expiry, publishes it as the Vault secret's
  new CURRENT version, then revokes the old key or deletes the old token.
- Upstream binds metrics (9096) on every interface; the OCI security list and
  host firewall keep it private.

## Access policy

Managed by `manager.GRU()`; the upstream allow-all `Default` policy is
deleted at first start.

- `operators`, `ops-automation` -> `gru-servers`: TCP 22 and NetBird SSH.
- `gru-servers` <-> `gru-servers`: ICMP and service health ports.

## Operator PC

Run on the PC (needs the `oci` CLI logged in to the TerraScale tenancy). The
key goes from Vault through a pipe straight into the client; it is never
printed or put in argv:

```sh
curl -fsSL https://pkgs.netbird.io/install.sh | sh && \
oci secrets secret-bundle get-secret-bundle-by-name --region sa-saopaulo-1 \
  --vault-id ocid1.vault.oc1.sa-saopaulo-1.ffvnrldqaaexa.abtxeljrlqoda2dl7r527hwngvx5k5j7lhfytswubkmx6rtg5f4mjtv4xzlq \
  --secret-name gru-1-netbird-operators-setup-key \
  --query 'data."secret-bundle-content".content' --raw-output | base64 -d | \
sudo netbird up --management-url https://netbird.terrascale.tech --setup-key-file /dev/stdin
```

## Login (M1)

Open `https://netbird.terrascale.tech/` for the NetBird dashboard. The owner
`mariogk@terrascale.tech` is NetBird's built-in local account; its password is
`gru-1-netbird-owner-password` in `gru-vault`. The dashboard uses the embedded
IdP at `https://netbird.terrascale.tech/oauth2`, client `netbird-dashboard`,
and the registered `/nb-auth` and `/nb-silent-auth` callbacks. The same IdP
supports browser SSO for `netbird up --management-url https://netbird.terrascale.tech`.

### Managed dashboard

The dashboard is always part of the ts-orch edge on the host serving NetBird.
It uses the unmodified static export in `netbirdio/dashboard:v2.94.0`, with
only upstream environment placeholders replaced by the fixed management and
OIDC settings. Go serves the site directly, so there is no nginx task, writable
container root or extra listener competing with TerraBase on port 8080.

The architecture-independent static layer is checksum-pinned:

- Image manifest: `sha256:44a250c04d91b46aa666de4b2b25602f0580b64dee0682fedfb9d012cb020ff7`.
- Static layer: `sha256:39224d252d48fc481e9107bf1a22171c2ef0268f44def5cda41e9ecdd82bbde6`
  (8,917,025 compressed bytes).
- Source and license: <https://github.com/netbirdio/dashboard/tree/v2.94.0> (AGPL-3.0).

At startup and every ten minutes ts-orch verifies the compressed layer cached
under its state directory's `netbird-dashboard/`. A missing or damaged cache
is downloaded from the public upstream registry, checked before parsing, and
replaced atomically. Failed fetches retry every fifteen seconds. The verified
site remains in memory throughout cache repairs or registry outages; the
first request during initial provisioning answers 503 with `Retry-After`.
A new ts-orch release containing a new pin upgrades the dashboard automatically.
No service apply or deployment setting is needed. The layer parser bounds
expansion and file sizes and rejects links and paths outside the static site.

The API, embedded IdP, gRPC, relay and websocket paths continue through the
existing reverse proxy; the public `/api/setup` remains forbidden. The
application's OIDC callbacks allow same-origin framing for silent login.
