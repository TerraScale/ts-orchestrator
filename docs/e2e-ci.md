# Node CI lanes

The ARM journeys run as independent matrix jobs. Every lane runs on each push to main. On pull requests, the paths job selects the runtime lane group for executable inputs; documentation and ops notes skip it. Workflow files, module files, build tooling and the shared E2E harness select every lane. Schedule retains its existing certificate and caller-key proofs and does not run the ARM matrix. In the table, Runtime inputs means this shared path selection, with main always selected.

The runner lanes consume containerd and runc versions from `deploy/image/debian/provision.sh` and archive checksums and NetBird metadata from `deploy/image/debian/base.json`. Both cold and warm caches install these verified archives before exercising the installer. `restore_runtime` performs verification and installation once per caller; cache keys include the image inputs.

`make generate` renders `deploy/m1/host-runtime.sh` from `deploy/m1/host-runtime.sh.in` and renders `internal/netbird/manager/client_pin.go` from the same image inputs. `make generate-check` rejects stale deployable copies. The SSH installer and embedded cloud-init script both execute that runtime script, including the checksum-verified NetBird archive; neither installs NetBird from a floating apt repository. Both the generated installer runtime and the manager execute the same service reconciliation script from `deploy/m1/netbird-service.sh`. It checks the live process executable checksum and arguments against systemd's structured ExecStart, repairs a service pointing at a different executable through NetBird's parameter-preserving reconfigure command, and restarts only when the running executable or command differs. A current process retains its PID. The NetBird archive sizes and extracted binary checksums also live in `base.json`.

One parallel `e2e-host-image` job selects the newest available published image release with both amd64 assets and a successful main image build. Draft, incomplete and removed candidates do not make an older qualified release ineligible. Main image CI publishes candidates as non-latest prereleases, so the gate's read-only token can download them without depending on short-lived CI artifacts. The selected pair of immutable asset IDs keys the image cache; the checksum is verified before every boot, including cache hits.

The job runs C2t's amd64 VM assertions for first boot, persistent-volume reboot, launch-release replacement and checksum rejection. Its result is required by `e2e-m1`. Changes to image inputs continue to build and boot the candidate through the existing `host-image` workflow. The pre-built smoke records its source SHA and provisioning differences in the summary. The 35 runner lanes and their single automatic rerun keep their existing deadlines and assertions. This is runtime archive parity plus Debian boot coverage: the runner lanes still use Ubuntu's kernel and distro packages.

The node-upgrade lane also exercises the NetBird host upgrade using the checksum-pinned prior archive in `base.json`. It checks replacement of a running older executable, an already updated disk file with an older live process, changed executable paths and arguments, a missing service, PID stability after reconciliation, and preservation of the persisted private identity and configuration created through NetBird's profile API.

On pull requests, e2e-build compiles the static agent once and the lanes download it, restore executable permissions and build their selected Go journey entry points from the shared ARM cache. On main, each lane builds both the agent and its helpers as before. The shared build.sh takes the output directory followed by explicit package paths, including ./cmd/terrascale-orchestrator when an agent is needed. The certificate lane fetches history and compiles its previous agent from the merge base with CHANGE_BASE (origin/main locally), then runs isolated edge processes with a stand-in authority. Its thirty-minute job budget includes that build and the real ten-minute lease. Startup deliberately observes a five-minute metadata window; it runs alongside the other lanes. Boot-order installs the pinned runtime without running the agent installer. Regional and postgres-preauth create their own isolated environments. Core, WebSocket, restarts, rollback, host-logs, monitoring and data-volume source the same installer/serving setup. Only data-volume runs the volume bootstrap before installation: it creates the mount requirements as service drop-ins, while the installer itself does not require a data mount. Its privileged volume drills run in private mount and network namespaces. The install fixture grows the verified 3 GiB filesystem to 32 GiB for the installed services’ disk reservations and adopts it without format permission, then the lane uses the shared setup’s per-command sudo. Only core saves the Go cache on main, avoiding concurrent uploads of the same cache key.

Fail-fast is disabled so the other lanes finish after a failure. Per-lane concurrency cancels obsolete work on the same ref. The aggregate check retains the name e2e-m1 and requires the complete matrix, including each lane's build, to succeed. A failed, cancelled or unexpectedly skipped matrix cannot pass the aggregate. Documentation-only PRs intentionally skip the matrix and its aggregate; all-green accepts those skips and directly rejects failure or cancellation in the paths job, shared build or matrix. All-green and publication's selected lane gate depend on the aggregate. Main may publish before its lanes finish only after proving that its merged PR passed all-green on the identical Git tree; see [Delivery pipeline](delivery-pipeline.md). Release concurrency is unchanged.

The shared edge certificate journey waits through a real ten-minute lease, so it runs as its own job with a thirty-minute limit, outside the matrix. On a pull request it runs when the edge, the mesh, the command wiring, its own journey, its documentation, the module files or the workflows change. On every push to main and once a day on a schedule it always runs. Publication requires the selected lane gate, either from the identical merged PR tree or from main. A pull request that does not touch those paths skips it, and that skip counts as success; a failure, a cancellation, or a skip when the paths did change fails all-green and blocks that run's lane gate.

The caller-key lifecycle and recovery journey runs in eight parallel x86 shards with fail-fast disabled and a five-minute limit per job. A separate build job compiles the overlay command and journey once and distributes those exact binaries. Cases have stable names and zero-based indices; case i belongs to shard i modulo eight. Every shard rejects an empty selection, and partition validation requires the sorted union to equal the unsharded list with no duplicates. Mutation-boundary families are split by operation, original interruption boundary and failure mode; all boundary cases still execute. Each shard records its execution time in the job summary. Locally, run `bash test/e2e/m1/callerkey/build.sh /tmp/caller-key-bin`, then `/tmp/caller-key-bin/callerkey run /tmp/caller-key-bin/terrascale-orchestrator` for all cases, or append `0 8` for shard zero; `callerkey list [i n]` lists the selected cases.

On PRs, caller-key-changes forwards the shared path classification, including runtime inputs and the caller-key contract documents, without a Go dependency walk. On main, selection uses `go list -deps -json` for the journey and the command with the journey's actual store overlay, for both the source and base revisions. Any change under a repository-local dependency directory, including local replacements under third_party, selects the journey. Embedded files, local module manifests and sums, the journey's complete directory, caller-keys.md, this document, ci.yml and the Go action are also inputs. Checking both graphs catches removed dependencies and files; directory matching includes newly added sources and package assets such as the region catalog. Graph errors fail the detector rather than skipping qualification. Detector logs list the computed inputs and matched changes. The journey also runs daily.

Both all-green and the selected lane gate require a successful detector. A true changed output requires the entire shard matrix to succeed; a false output permits a successful or skipped matrix. Detector failure or cancellation, an absent or invalid output, and any failed, cancelled or unexpectedly skipped required shard block both gates. All-green also rejects failure or cancellation in every other dependency. Scheduled runs qualify the journey but cannot publish binaries or release: the publication build runs only on push, and release-publish additionally requires main, publication marked required and either the identical merged PR's successful all-green or successful main lanes.

To add a lane, create its entry script under test/e2e/m1/, source setup.sh if it needs the installed services, then add exactly one matrix entry in .github/workflows/ci.yml:

~~~yaml
          - {lane: example, entry: example.sh, timeout: 10}
~~~

Its binary argument is the lane's agent; sibling helper binaries are in the same directory. A lane with Go helpers lists their package paths in the same matrix entry, for example packages: "./test/e2e/m1/example". Helper directory basenames must be unique. Record its proof, timeout and path condition in the table. Do not append it to run.sh.

For a disposable local host, build with:

~~~sh
test/e2e/m1/build.sh /tmp/m1-bin ./cmd/terrascale-orchestrator
bash test/e2e/m1/run.sh /tmp/m1-bin/terrascale-orchestrator
~~~

Substitute the selected entry script. Install-based lanes require passwordless sudo and modify the disposable host.

## Oracle-mode node harness

The oracle-regions lane runs the real agent exactly as `deploy/m1/ts-orch.service` starts it, with every Oracle and cloud dependency replaced by a test-only stand-in. The harness is the Go package `test/e2e/m1/oraclehost`; another lane reuses it by calling `oraclehost.Main()` first in its own `main`, then `oraclehost.New` for a fleet, `Boot`, `WaitReady`, `Health`, `Exec`, `Restart` and the Vault observers. The lane runs inside `unshare --mount --net`, so the fleet's bridge, namespaces and stand-ins never touch the runner's own network or Azure metadata service.

| Production dependency | Stand-in |
|---|---|
| Host | One network namespace per host on a private bridge (VCN `10.204.0.0/24`, gateway `10.204.0.1`), with its own mount and UTS namespace: hostname `ts-<region>-<n>`, tmpfs `/run`, `/var/lib` and `/etc/systemd`, per-host `/var/lib/ts-orch`, `/var/lib/containerd` and `/usr/local/bin` (agent, containerd and its runc shim), and its own containerd |
| systemd | A supervisor that reads `ts-orch.service` from the embedded `deploy/m1` files and refuses any `[Service]` key it does not reproduce. It runs `ExecStart` with the systemd environment (`PATH`, `LANG`, `NOTIFY_SOCKET=/run/systemd/notify`, `INVOCATION_ID`), `PrivateTmp`, `ProtectHome`, `ProtectSystem=full` with `ReadWritePaths` and `ConfigurationDirectory`, `NoNewPrivileges`, `UMask` and `LimitNOFILE`; readiness is the `READY=1` notification, `Restart=always` with `RestartSec`, and a restart is SIGTERM with `TimeoutStopSec` before SIGKILL. Sandbox keys that only add seccomp or capability filters are accepted without emulation |
| DMI | A tmpfs over `/sys/class/dmi/id` with `chassis_asset_tag` `OracleCloud.com` and `board_asset_tag` set to the instance OCID |
| NetBird | A `wt0` dummy interface holding the host's `100.104.0.x` address, host routes to every peer's `wt0` address through its VCN address, and `ts-<region>-<n>.nb.ts.internal` names in the namespace's hosts file. No `netbird` binary is installed |
| IMDS | `169.254.169.254:80` on the bridge, answering `/opc/v2` only with `Authorization: Bearer Oracle`: instance document, id, display name, region, canonical region name, VNIC list (private IP and VCN CIDR) and the instance identity certificate, key and intermediate. It tells hosts apart by source address |
| OCI federation | `auth.<region>.oraclecloud.com/v1/x509` for every fleet region over TLS, reached through the namespace's hosts file and a CA bundle bound over `/etc/ssl/certs/ca-certificates.crt`. It accepts only the instance identity certificate it issued |
| OCI Vault | `secrets.vaults.sa-saopaulo-1.oci.oraclecloud.com` bundles by name and `vaults.sa-saopaulo-1.oci.oraclecloud.com` list, create (409 on an existing name), get and etag-checked update. It starts with every secret the embedded first-party services and alert delivery reference; the mesh key, TerraBase token and `ts-orch-join-<region>` material are created and published by the hosts themselves |
| GitHub OIDC | `token.actions.githubusercontent.com/.well-known/jwks` with the lane's signing key, so the lane can read each host's authenticated HTTPS observation with a signed token |
| Container registry | `registry-1.docker.io` serving, by digest only, the workload image the lane fetched before it entered its private network |

The lane boots the three founders first and the workers once Vault holds each region's join material, because a worker that finds no material waits a full join period. It applies the workload only once every manager's mesh is up and every region answers `ts-orch status` over it, because `ts-orch service apply` on a host whose mesh has not started yet applies to that host's swarm only, and the other regions' managers then never route anything. This six-host lane does not install an orchestrator release: the release handler's recovery step links and starts a systemd timer and reads `ts-orch.service` through `systemctl`, which needs a real systemd per host.

## Credential isolation

The host-credentials lane uses mount and network namespaces with an actual tmpfs and disables swap on its disposable runner. The updater-preflight lane runs the alert-preparation assertions with the same memory protection. Together they cover every assertion in the local credential-vm harness without requiring KVM or QEMU in CI. That harness remains available for local machines whose active swap must stay untouched; it adds no VM-only assertions. The monitoring lane also disables swap and prepares protected disposable credential files before starting the real relay. Its malformed journey-state assertions continue to exercise alert acceptance independently of journey observations.

Release-contracts runs its short namespace/API journeys together. Metadata-upgrade seeds the generated metadata rules before sourcing setup.sh, modeling an existing host with a protected metadata boundary, then exercises the real installed systemd unit. Setup creates persistent state for certificates before installation, so it intentionally does not represent an installer-fresh host. Release-contracts covers fresh-host rule creation in its isolated installer journey. Metadata-upgrade moves the NTP stand-in into a peer network namespace before upgrading: metadata prerouting protections correctly reject traffic to a runner-local metadata address, while the peer models the real external clock endpoint. Core run.sh and operator startup.sh remain identical to the merged base.

## Publication on main

A successful main push releases only when the build emits publication=required, e2e-m1 succeeds, and the caller-key detector and shard gate described above pass. The release-input comparison includes the executable dependency graph for both architectures (source, native files and embedded assets), module manifests, Makefile, .github/workflows/ci.yml, .github/actions/go/action.yml, and the release qualification/audit scripts listed in scripts/ci/release-inputs-changed.py.

A change limited to .github/ can therefore release: the CI workflow and Go action are explicit executable inputs. Other workflow files, docs/ and test/ alone do not require publication when a complete, admissible retained main ancestor proves those executable inputs unchanged. An absent, invalid or unreadable retained baseline requires publication even for documentation-only or journey-only changes. The comparison is against retained qualification, rather than just the previous commit.
