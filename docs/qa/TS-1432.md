# TS-1432 qualification: a read-only per-service, per-region digest table

Ticket: `ts-orch inspect digests [--region R]` printing service, region,
desired digest, observed running digest, since, and match across
gru/sjc/fra. This page records what the existing read paths prove, where
the contract stops, and the live evidence gathered on 2026-11-05. Nothing
was shipped; the conclusion is a blocker, not a design.

## What each existing read path actually proves

### Native service roles (terrabase, ts-auth): `releases/services/<role>/status.json`

`releasechannel.ServiceStatus` (`internal/releasechannel/service.go`) is
written only by the region's authority leader
(`serviceReleases.report` in `internal/app/service_releases.go:746-849`).
Provenance of each field:

- `digest` — the **claim digest of the artifact the leader admitted**: the
  signed delivery artifact claim in `releases/services/<role>/release.json`
  names the binary SHA-256; the leader verifies the claim's signature and
  that the staged bytes hash to it (`delivery.Service.AdmitClaim`), then
  reports that digest. It is a desired/admitted digest, not an independent
  runtime observation.
- `state: complete` — this is the only field that embeds a **verified
  running observation**: the readiness gate (`nativeHistory.proofs` →
  `observeNativeProofs`, `internal/app/native_history.go:662-720`) refuses
  `complete` unless every expected replica's host report matches the
  intent's digest, generation and session, is `running`, is fresh
  (`host.ReportMaxAge`) and is double-read unchanged. A historical
  `complete` is demoted back to `rolling` on every report pass unless
  fresh target proofs from every replica still exist
  (`service_releases.go:760-773`).
- `source_revision` — the claim's git SHA (a source identity, not an image
  digest).
- `issued_at` — when CI signed the claim; **not** a process start time.
- `updated_at` — when the leader last wrote `status.json` (written on
  change or at least every `PinRefreshInterval`, 30 s). It measures
  telemetry freshness, not uptime.

So for a native role the existing contract **can** truthfully answer
"desired digest = X and the leader currently proves every replica running
X" — by combining `digest` (desired) with `state` (the proven-running
gate). What it **cannot** answer is an independent "observed running
digest" value: no reader-visible field carries a digest observed from the
runtime separately from the admitted claim. `release.json` (the claim) and
`status.json` (the report) both originate from the same admitted digest.

### Orchestrator binary: `releases/orchestrator/channel.json` + `status.json`

`channel.json` is the CI-signed channel (source revision, run number,
signed receipts). `status.json` (`releasechannel.Status`) is again the
leader's report; `state: complete` means the rollout gate passed for the
channel's receipts. The status carries **no digest field at all** — only
`source_revision` and `run_number`. A digest column for the orchestrator
would have to be derived by matching receipts in the signed channel, and
"running" again only as a state, not an observed value.

### Container/app roles: desired-only, no operator read path

App image releases write `releases/services/<role>/containers/<arch>/
container.json` (signed claim, has `image`) and `status.json`
(`releasechannel.ContainerStatus`, has `image` + `state`). Desired image
digests exist here, but the mesh state API that reads them
(`releasepush.Digests`, subject `ts.release.mesh.state`) requires an
app-digests workflow OIDC token — an operator CLI cannot call it read-only
today, and the container status objects are per-architecture and not
exposed by any operator command.

### Why a naive table is wrong (the rejected implementation)

An earlier draft of this ticket derived "desired" and "running" from the
same `ServiceStatus` object (`digest` for both). That is tautological: a
stale `complete` report for an old claim would always show
desired == running == old digest, silently hiding drift. It was removed
before commit; nothing shipped.

## Blocker

`ts-orch inspect digests` with an **observed running digest** column
requires a telemetry contract that reports, per service and region, a
digest actually observed from the runtime (per-replica host reports exist
internally in `TS_NATIVE_RELEASES`/host reports, but no reader-visible
object exposes an observed digest distinct from the admitted claim). Any
implementation today must either (a) print admitted-claim digests and
leader states honestly labeled, or (b) invent the missing authority
contract, which this ticket forbids. A faithful command could still ship
columns CELL / ROLE / ADMITTED DIGEST / STATE / REPORTED AT, but the
ticket's "observed running digest + since" cannot be truthfully filled
from the existing read-only contract.

## What would unblock it

Publish (in the leader's existing `status.json` pass) an observed digest
field sourced from the readiness gate's per-replica host reports — the
same reports `nativeHistory.proofs` already verifies — with the
observation instant, per role and cell. That is a one-field contract
extension in the report writer plus this reader; it needs its own ticket
because it changes the status contract producers write.
