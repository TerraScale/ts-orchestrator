# Regional production monitoring

1. Validate without installing: `deploy/observability/production/install.sh --check`.
2. After the green orchestrator release reaches every host, deploy the checked assets with `deploy/observability/production/install.sh --fleet`. This installs one Prometheus, clustered Alertmanager and delivery relay on the first inventory host in each region. It runs every host's preflight before changing any host, installs hosts that already run monitoring (today `ts-gru-1`) before new ones, and finally requires every Alertmanager to report all inventory backends as cluster peers. It provisions no capacity or credentials. `install.sh --preflight <SSH-host>` runs one host's checks alone and prints `existing` or `new`.
3. On each monitoring host, inspect `systemctl status ts-prometheus ts-alertmanager ts-alert-delivery` and query `curl -fsS http://127.0.0.1:9090/api/v1/targets`.

`hosts.txt` is the only host and region inventory. `go run -C scripts/monitoring . <directory> "$PWD"` renders every backend configuration and every region's rules from it. Source rule files are templates; Prometheus loads the generated `production/rules.yml`. Each backend independently scrapes the entire fleet, evaluates all regions, and sends identical alerts to all three Alertmanagers. Alertmanagers use memberlist gossip over NetBird TCP/UDP 9095 and their notification log to deduplicate delivery through one local relay per group. Their HTTP listeners bind loopback and the host's NetBird address on 9093. Losing one running region leaves the other regions evaluating and delivering. Prometheus and the delivery relay bind loopback; fixed metrics proxies on the existing NetBird-only 9108 listener let every backend check every other backend without exposing Prometheus query or administration APIs. The managed metrics policy permits regional server groups to scrape each other.

The SSH host argument must resolve through existing trusted SSH configuration. Local rendering needs Go; remote hosts need Python 3, systemd, sudo, curl, tar, sha256sum, useradd, timeout and grep. `/usr/local/bin/ts-orch` must already support the fixed monitoring proxies and `alert-delivery`. The installer checks all hosts' task inventories and orchestrator proxies before modifying installed monitoring. Installation has not been run against production by this change. Existing data directories are retained. Unchanged reruns start units without restarting them. The installer downloads official pinned binaries, verifies their checksums and validates every rendered configuration before changing installed files.

`make observability-check` and the monitoring E2E lane run the same renderer and Prometheus rule evaluator. The renderer parses PromQL, rejects region filters in templates, preserves region labels through aggregation and joins, and rejects metrics outside local exporter source strings, the foreign-service catalog and recording rules. `metric-catalog.txt` contains foreign-service metric contracts; update it with the service exporter change. Native counters can be absent until their event occurs. The monitoring lane runs three real Prometheus, three gossip-clustered Alertmanager 0.34.1 with the production 15 s peer timeout and 10 s notification deadline, `group_wait` divided by ten and `group_interval` and `repeat_interval` divided by 2.5, so every interval still exceeds three peer waits (the renderer checks the lane keeps the production deadline-to-peer-timeout ratio; Alertmanager's retry backoff does not scale), three real relays (only their listen, state and provider addresses differ) behind an HTTP/2 push provider like the real one and a three-node JetStream cluster built from the mesh's own server options. It scrapes the actual mesh metrics through the 9108 proxy, checks old non-zero counters stay quiet on first activation, withholds email and pages while the mesh token is missing and uses it once it appears without a restart, delivers one topology incident as exactly one firing and one resolved notification, stops fleet email at 12 and pages the exhausted budget by push, loses GRU's Prometheus, Alertmanager, relay and budget node and delivers each counter group once through the surviving relays, keeps pushing 13 concurrent notifications while the budget has no quorum, answers a push the provider never replies to with one 502 that Alertmanager retries before the next peer sends, checks a global fast burn inhibits the regional one, and checks an old-layout relay on the new binary still emails from its own ledger. The rule journey evaluates each region's loss from every backend, checks regional and global SLO burn matching (including 300 requests/hour per region with 100% errors) and inventory disappearance, rejects an invented metric, a pinned region and a `group_interval` under the peer waits, and adds an inventory region to prove it receives rules automatically. Every Alertmanager, in production and in the lane, runs a 5 s `--cluster.pushpull-interval`: notification-log gossip is best effort and can miss a peer after a burst, and with the default 60 s push-pull that peer sent the group a second time when its 15 s peer wait ended. The renderer requires the push-pull to stay under half the peer timeout in both.

Alertmanager uses gossip and deterministic notification ordering, without electing a notification leader. `AlertmanagerClusterDegraded` pages once (region `global`) when an Alertmanager reports fewer cluster members than the reachable Alertmanagers, or failed peers while every Alertmanager is reachable, for five minutes: a split or never-formed cluster otherwise delivers each page once per partition. `PeerTopologyAttestationDown` holds two minutes, like the other scrape-down alerts, so one brief cross-region path failure does not page; the installer preflight requires the real peer-topology exporter (127.0.0.1:9097, through the 9108 proxy) on every inventory host, including the `-2` hosts. An isolated partition can deliver independently; exactly-once delivery is not guaranteed across partitions or a crash during provider acceptance. Each Prometheus sends to every Alertmanager so loss of an entire region leaves delivery working. Readiness, public certificate and production-journey signals aggregate relay perspectives into one global alert per service or journey outage. Each Alertmanager waits its peer position times the 15-second peer timeout before it checks the gossiped notification log, so a group that changes state inside that wait would be sent again from a stale snapshot. Every route's `group_interval` therefore exceeds the backends times the peer timeout (45 s with three backends), and the push deadline of 10 s, including connect, is under that 15 s peer timeout; the renderer refuses either violation. The topology route keeps a 5-second `group_wait` for a fast first page and a two-minute `group_interval`, which holds for up to seven backends. Alert email has one fleet budget, described below; push never waits for it. The heartbeat verifies one deduplicated fleet delivery path; its freshness uses the newest completed probe across relays, while backend-down alerts cover every relay listener. Push remains independent. Relays prepare the existing approved Vault references before starting and then use local tmpfs credentials on delivery. Restarting a relay while the Vault region is unavailable remains unproven.

The `host-storage` scrape also collects `ts_orch_edge_responses_total{protocol,code}` with discovery's `host` and `region` labels. Its sample limit covers both HTTP listeners' bounded three-digit status codes plus host metrics. Each response is counted when its final status is committed, including local 502/503 errors, HTTP/1 upgrades as 101 and successful extended CONNECT tunnels as 200. Interim 1xx responses do not add another count. Only observed protocol/code pairs are exported; no route, hostname or tenant labels are added. This job collects the counter once per host; no additional scrape is needed.

To count edge 502s during a five-minute release window, evaluate at the window's end:

```promql
sum by (region) (increase(ts_orch_edge_responses_total{code="502"}[5m]))
```

Use `sum by (host, region)` to locate affected hosts. `increase` adjusts for process counter resets and extrapolates between scrapes; a new series needs at least two samples, so the first observed failures may not be counted in the window.

Operational alerts use existing backup/replication metric names. Backup pass failures use `terrabase_backup_failures_total`. `TerraBaseBackupHoles` covers both hole counters explicitly: `terrabase_backup_holes_total`, which the TerraBase release in production exports today (read from the live ts-gru-1 Prometheus on 2026-11-15), and `terrabase_backup_holes_recorded_total`, which TerraBase main exports since terrascale #2012 (main also exports the gauge `terrabase_backup_holes`, which no rule reads). Failed daily restore drills use the existing `terrabase_backup_drills_total{result="failed"}` counter; `TerraBaseBackupDrillStale` fires when the same counter shows no completed drill for twenty-six hours. Backup lag warns at sixty seconds (`TerraBaseBackupLag`) and pages at three hundred seconds (`TerraBaseBackupLagCritical`), both held five minutes, and `TerraBaseBackupSnapshotAge` warns when the newest Tigris snapshot of the backup bucket (`terrabase_backup_bucket_snapshot_seconds`, zero on members that take none) is older than twenty-six hours. Missing operational series cannot prove backup health. Native event counters appear only on their first event, so counter rules combine the windowed `increase()` with a first-observation clause: a nonzero series that did not exist one window ago fires when the same scrape target (`instance`) was already scraped successfully one window ago. A series that appears in a process Prometheus already watched therefore pages at once; old nonzero values found when Prometheus first starts, or when a target returns after an outage longer than the window, do not. The clause ages out after one window; later increases and counter resets followed by failures go through `increase()`. A first sample that is already nonzero while its target was absent or down one window ago (a process that starts with the event already counted) is the remaining gap: it does not page. terrascale C122 (#2110) makes TerraBase and ts-auth export their alerting counters at 0 from process start; once that release runs in production, each counter rule drops its `or (... unless ... offset ...)` clause and keeps plain `increase()`, one expression line per rule. `terrabase_replica_verifications_total` keeps the clause until its counter is seeded too (terrascale #2046). `TerraBaseMetricsDown` and `TerraBaseHostMetricsDown` require two minutes of failed scrapes before firing.

Alertmanager sends critical firing and resolved webhooks to `http://127.0.0.1:9094/alerts`. Critical firing groups email and push at once; resolved groups only push, since recovery needs no action. Warnings (SLO slow burns, missing telemetry, storage warnings) go to `/alerts/digest` as one group without resolved notices: at most one digest email per 24 hours and never a push. Readiness must fail for five minutes and recover for ten before the alert changes state, so probe flaps do not page. The installer manages the relay alongside Prometheus and Alertmanager and checks its `/healthz`; this proves listener readiness and usable credential files, not external delivery. No installation, activation or live delivery proof is claimed here. A controlled firing alert and its resolution still need verification against the deployed release, provider responses and the owner's actual inbox/phone receipt.

Push is never capped and never waits for email: the relay pushes every valid critical notification at once and answers HTTP 202 after the push succeeded. That push is bounded to 10 s including connect, under the peer timeout, and its HTTP/2 connection sends a ping after 2 s without a frame and closes 2 s later without an answer, so a silently dead connection fails only the pushes in flight on it, so the answer returns before the next peer sends and Alertmanager writes its notification log, never retries a delivered notification and always sends the RESOLVED notification. If the push itself fails the relay answers 502 and Alertmanager retries; the email reservation of the first attempt makes the retry skip email. Email runs beside the push and is gated only by the budget: at most 12 per rolling hour and 288 per rolling day across every relay, group and status, reserving the rest of the shared 1000/day quota for sign-in; each group/status is emailed at most once per four hours, matching `repeat_interval`, and every digest shares one 24-hour slot. Older payloads without `groupKey` use sorted fingerprints or labels.

On a fleet backend (installed with `--fleet`, which writes `/etc/ts-monitoring/production/alertmanager.env`) every relay reserves email in the JetStream key-value bucket `ts-alert-email` (three replicas, one per region) on its host's mesh, `nats://127.0.0.1:4223`, as the mesh user `ts-alerts` in its own `ALERTS` account, which holds nothing else. The reservation is a compare-and-set on one key: relays that reserve at once re-read, so the fleet never exceeds the budget, and a region loss leaves the bucket writable on the remaining two replicas. The mesh writes the user's token to `/var/lib/ts-orch/mesh/alerts.token`; the relay's root `prepare` step copies it to `/run/ts-alert-delivery/ts_alerts_nats_token_file` at start, and `ts-alert-delivery-token.path` runs `alert-delivery copy-token` when the mesh writes the token later. That copy does not read Vault; the oneshot restarts if the copy fails. Only `--fleet` writes `alertmanager.env`; installing one host does not, and removes a leftover file. The relay reads the copied token on every reservation, so a token that appears after the relay started is used without a restart. A host without `alertmanager.env` is a lone relay (today's GRU-only install): it keeps reserving from its own `/var/lib/ts-alerts/email-ledger.json`, which is the whole fleet budget there, so the new release alone never withholds its email. A reservation is written before sending and expires 50 seconds after it is taken plus its window, so a failed or ambiguous attempt still consumes it and a lost provider response never sends twice. When that write fails or its acknowledgement is lost, the relay reads the reservation back once and never writes again: if the reservation is there the write landed and the email is sent; if it is not there, or the read-back fails, the email is withheld and counted as `reason="budget_unavailable"`. When the budget is spent the relay withholds the email and counts `terrascale_alert_delivery_email_withheld_total{reason="budget_exhausted"}`, which pages `AlertDeliveryEmailBudgetExhausted` (critical, region `global`) by push; an unreachable bucket or a missing token counts `reason="budget_unavailable"` and pages `AlertDeliveryEmailBudgetUnavailable`. Both counters are exported at 0 from relay start. HTTP 202 means the push was accepted; it does not prove email, inbox or phone receipt.

`TerraBaseBackupLag` and `TerraBaseBackupLagCritical` hold for `5m` and `TerraBaseReplicationSendLag` for `5m`. With 15-second scrape and evaluation intervals plus the 30-second initial `group_wait`, a newly observed sustained lag has a nominal initial notification budget of about 6 minutes (15s scrape + 15s evaluation + hold + 30s grouping). An alert that joins an existing group waits for its five-minute `group_interval`. This is configuration timing, not measured end-to-end delivery; provider latency, retries and outages can extend it.

Missing native request counters produce telemetry warnings instead of measured availability. A failure of one monitoring region leaves the other installed monitoring regions evaluating and delivering independently. Actual production failover and recipient receipt still require post-rollout proof.

The relay probes only fixed public HTTPS endpoints: `https://api.terrascale.tech/readyz`, `https://auth.terrascale.tech/readyz`, and `https://dash.terrascale.tech/readyz`. Each scrape runs the three probes concurrently with verified TLS, no environment proxy, no credentials, no redirects, a three-second timeout per probe and a 16 KiB response limit. API/auth require HTTP 200 JSON with `status=ready`; dashboard requires HTTP 200 JSON with `status=ok` and both `dependencies.ts-auth=ok` and `dependencies.terrabase=ok`. Timeout, TLS failure, non-200 or invalid expected JSON yields zero. Only fixed service labels are exposed; errors and URLs are never metric labels. Caller-selected targets are not supported.

`ServiceReadinessFailed` pages critically for any of the three services after five minutes of sustained readiness failure and resolves after ten minutes of recovery. With 15-second scrape/evaluation intervals, at most three seconds probing, the five-minute hold and the initial 30-second grouping wait, the first notification goes out five and a half to six and a half minutes after readiness fails. Existing groups, retries and provider delay can extend delivery. Readiness is a public endpoint check, not a full user operation or fleet SLO. These gauges manufacture no request successes; native SLO counters are collected separately. Relay/host failure can remove readiness samples altogether; this rule alone does not detect missing series.

The relay observes executed production journeys independently of scrapes every thirty minutes, with a thirty-five-second total deadline and three seconds per API call. A refresh makes at most eleven unauthenticated GitHub API calls (one runs listing and at most ten job listings), at most twenty-two per hour across relay restarts. The next refresh time is reserved durably before API access, using the same locked, atomic state-file pattern as the email ledger. Last-good results and observation timestamps are persisted in `/var/lib/ts-alerts/journey.json`. An unreadable or malformed file never prevents the alert endpoint opening: the observation is unknown (`observed=0`), missing telemetry warns, no journey API requests are made, and one line is logged until recovery. The file is checked each minute while malformed; repairing or replacing it restores observation subject to its durable reservation. Reservation or state errors prevent API access. It preserves the last successful observation on lookup errors and exports its age; missing telemetry warns after the observation is over sixty-five minutes old for ten minutes, or the completed journey is over thirty-six hours old. A restart inside a reserved interval makes no API calls; the first start without state allows one refresh. Lookup errors retain the last good observation and its reserved schedule. Provider refusals extend that reservation to the latest of the thirty-minute interval, `Retry-After` (seconds or HTTP date) and `X-RateLimit-Reset`.

Backup age applies only to members with a positive last-success timestamp. A member that has never shipped files does not trigger this age rule. Database scrape failures use their dedicated alert; other application targets use the generic alert. Kernel OOM kills warn on any increase over fifteen minutes and identify the host.


The production journey gauges describe the **production journey's last result from GitHub**. They do not attest to alert delivery.

`AlertDeliveryHeartbeat` always fires with `delivery_probe=heartbeat`. Alertmanager routes it through the normal local relay receiver every five minutes, in its own group, with no initial group wait. The relay removes probe-labelled alerts before real notification handling and sends them to a bounded background worker. For this label alone, it publishes a random nonce to ntfy, then polls ntfy's cached-message API and verifies the same message ID, topic and nonce. Completion is persisted atomically to `delivery-probe.json` and exported as `terrascale_alert_delivery_probe_completed_timestamp_seconds`; zero means no trustworthy completion. A scrape does not initiate a probe.

The probe topic is `ts-probe-` plus the unpadded base64url HMAC-SHA256 of the fixed label `terrascale-alert-delivery-probe-v1`, keyed by the real push-topic secret: 52 characters from the push service's topic alphabet, inside its 64-character limit. It uses the same secret reader and push service as real push. Knowledge of a topic is this push service's credential. The derived topic has no human subscribers, is never shown by the subscription command, is not guessable without the real secret, and is explicitly checked against the real topic before publication. Probes never publish to the real topic, send email, or notify a person. They never fail real alert deliveries and never use a real delivery's handler; a probe that starts first can hold the shared credential provider for its own bounded request, at most 12 seconds.

A durable locked reservation permits at most one attempt per five minutes across restarts: at most 12 Vault topic reads and 24 push API requests per hour (one publish and one read-back per attempt), with a twelve-second total attempt deadline and 64 KiB response bounds. No retries are made; failed attempts consume their reservation. Invalid probe state reports no trustworthy completion and suppresses probe requests until repaired. Successful completions older than fifteen minutes page critically without an additional hold; zero or absent completion telemetry holds fifteen minutes before paging.

Probe failures log the push-stage error as `result=push_failed`, without provider response bodies or credentials. Real email refusals increment the separately seeded `terrascale_alert_delivery_email_refused_total` counter and page `AlertDeliveryEmailRefused`; logs distinguish `email refused by admission` from `email refused by provider`. A refused email is not a missing push probe.

This probe proves rule evaluation → Alertmanager routing → relay → push publish → push API read-back. It does not prove email or actual phone/inbox receipt, recipient subscription, or public app behavior. Its stale or missing alerts travel through the normal path: if that path is broken, these alerts cannot arrive either. The [outside probe](../../outside-probe/README.md) runs on Cloudflare with a five-minute cron trigger. Its Durable Object stores consecutive observations and page timestamps; an independent alarm watches for ten minutes without a completed report. GitHub Actions provides a manual report only. The Worker secret `TS_ALERTS_NTFY_TOPIC` is the same value as vault ref `gru-1-ts-alerts-ntfy-topic`.

The rule lane models a normal task restart as 40 seconds down, including the one-replica auth service briefly at 0 of 1. Both two-minute scrape holds and the five-minute coverage hold exceed this modeled interval, and the evaluator verifies they remain silent. Forty seconds is the lane's restart scenario, not a measured production restart promise. A rollout that exceeds a hold can page and should be investigated. The runtime lane seeds the real agent assignment database, uses actual containerd tasks and the real exporter, kills the assigned dashboard process without a task manager to restart it, and requires expected=1, running=0, discovered=0. It also runs the real relay binary with malformed journey state inside isolated mount/network namespaces.

## Rollback

Every install saves the actual host files after config validation and before changing installed state: `/var/backups/ts-monitoring/before-XXXXXXXX`. The installer prints that path. The root-only snapshot contains `/etc/ts-monitoring`, the monitoring binaries, the five monitoring unit files and their active/enabled states. It preserves a mixed-revision installation exactly; a previous Git checkout cannot reconstruct that installation. Record the printed path per host. For an installation predating snapshots, capture it first with `sudo bash deploy/observability/production/snapshot.sh` on the host.

1. Before restoring, silence **all old rule alerts** on every running Alertmanager for ten minutes: `/usr/local/lib/ts-monitoring/amtool silence add --alertmanager.url=http://127.0.0.1:9093 --duration=10m --comment='monitoring rollback staleness window' 'alertname=~".+"'`. Record the IDs. The silence must cover the restore and at least five full minutes after restored Prometheus is ready: fleet series remain queryable during Prometheus' five-minute staleness window and can fire restored rules by themselves. Extend the silence before it expires if the restore takes longer than five minutes.
2. Revert the orchestrator release if that release is also being rolled back. On each changed monitoring host, run `sudo bash deploy/observability/production/restore.sh /var/backups/ts-monitoring/before-XXXXXXXX` from this revision, using that host's recorded snapshot. Restore stops the managed units, removes the forward config/binaries/unit files, extracts the captured files, reloads systemd and restores the recorded enabled and active states. A previously uninstalled host returns to having no monitoring install. The renderer rejects a rule metric that no exporter provides.
