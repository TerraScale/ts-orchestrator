# Existing gru host monitoring (TS-820)

1. Validate without installing: `nice -n 19 deploy/observability/production/install.sh --check`.
2. Deploy the monitoring backend to the existing host: `deploy/observability/production/install.sh ts-gru-1`.
3. On that host, inspect `systemctl status ts-prometheus ts-alertmanager ts-alert-delivery` and query `curl -fsS http://127.0.0.1:9090/api/v1/targets`.

The SSH host argument must resolve through existing trusted SSH configuration. The host needs systemd, sudo, curl, tar, sha256sum, useradd, timeout, grep and outbound HTTPS. `/usr/local/bin/ts-orch` must already be a release supporting `alert-delivery`. No host, IAM, credentials or paid capacity is provisioned. Installation has not been run against production. The installer creates the dedicated ts-prometheus, ts-alertmanager and ts-alerts users if absent and installs/enables/starts all three systemd units; unchanged reruns start them without restart. Existing data directories are retained. Validation downloads official binaries into a unique temporary directory and deletes only that directory.

Prometheus 3.15.0 and Alertmanager 0.34.1 are pinned with SHA256 hashes from their official GitHub release `sha256sums.txt` files (retrieved 2026-10-23); 0.34.1 was the official latest stable Alertmanager release at discovery. Both amd64 and arm64 are supported. Before installed state changes, the installer checks bounded global help for `alert-delivery` and requires its `--help` usage error (exit 1), never invoking the bare daemon as a probe. The pinned tools validate all configs and rules before installation changes any host files. `--check` validates configs locally without probing an installed ts-orch. Configs live under `/etc/ts-monitoring`; systemd uses dedicated unprivileged users and state directories. All three HTTP listeners bind loopback; Alertmanager clustering is disabled. No secrets are in these files.

Prometheus retains 35 days of data. Disk consumption depends on real series cardinality: check available space before activation and measure actual growth. The reported 21 GiB spare memory is not a measured monitoring memory budget. This is a single-node backend on ts-gru-1, not an independent availability monitor: host failure also stops its alert delivery.

The `application-slo` job reads HTTP discovery from every host's NetBird agent on port 9108. Expected inventory comes from the local SwarmKit agent's persisted manager assignments whose desired state is RUNNING, before container identity validation. It does not come from observed processes or controller registrations. A read-only snapshot of the agent's assignment database works on managers and workers, including after restart and while the manager is unreachable.

Each host exports three gauges for each of terrabase, ts-auth and ts-dashboard, with host and region supplied by host discovery:

| Gauge | Definition |
| --- | --- |
| `ts_host_service_tasks_expected` | Locally assigned tasks with desired state RUNNING, regardless of process existence or identity validation. |
| `ts_host_service_tasks_running` | Containerd processes in RUNNING state that pass recorded task, service and admitted-image identity checks. |
| `ts_host_service_tasks_discovered` | Valid running tasks emitted by HTTP metrics discovery, including failed targets whose local metrics listener cannot be found. |

`ts_host_service_task_identity_rejected{reason}` counts rejected identities with only `task_identity`, `service_identity` or `image_identity` as reasons. Each rejected task is logged once while its container exists. Rejection cannot lower assigned-expected inventory. Discovery and container enumeration are cached for five seconds. Four concurrent discovery/proxy requests are admitted; excess requests return 503. Targets identify host, region, service and task instance. The proxy forwards only the task's loopback exporter, without caller headers, redirects or credentials, and bounds its response. An unavailable auth listener stays a failed target.

Coverage compares assigned-expected with the count of targets whose scrape is UP, grouped by host, region and service; missing targets count as zero. Its five-minute hold covers disappearing discovery entries and vanished processes. Database and other task scrape failures independently page critically after two minutes. A separate fifteen-minute absence rule names each configured host even if every series for that host disappears. The one-replica authentication service runs on one host; no rule expects it on every node. TerraBase and dashboard are checked wherever assigned, and auth only where assigned.

The existing writer still refreshes `/run/ts-orch-observability/targets.json` alongside the new exporter. Deployment order is **agent release everywhere, then monitoring configuration, then removal of the writer in a later change**. The installer leaves that file intact. This preserves the installed file-discovery configuration between agent rollout and configuration cutover. The writer's manager lookup, atomic file replacement, permissions and five-second cadence are retained; its file-specific runtime query retains the installed service lookup and target filtering.

The installer checks every discovery endpoint and requires all expected gauges before changing monitoring. `hosts.txt` is the installer's host inventory. One check compares its set with the scrape configuration, named absence rules and rule fixtures before local validation or remote installation. The lane runs the same check and proves a mismatch fails. Adding or removing a host requires updating those four sets together, then running the check and rule evaluator before installation. The remote archive includes fixtures so the same check runs on the destination. Python 3 is required. After cutover, compare assigned tasks with discovery and healthy targets for each actual placement.

The `host-storage` job collects CPU counters, memory totals and availability, kernel OOM kills and systemd restart counters for platform services, containerd and NetBird, alongside disk and edge evidence. Systemd counters reset when systemd unloads a unit or the host reboots; alert evaluation uses counter increases. Unavailable runtime evidence fails the scrape rather than reporting zero.

The peer-topology endpoint also reports mesh metadata observation, leader availability and effective quorum availability from the embedded broker. Certificate probes verify the public HTTPS chain for each service and report its earliest expiry; verification failure reports zero. The relay reads the latest executed `journey` job from the production workflow through GitHub's public API, excluding skipped jobs; observations are refreshed every thirty minutes. Unavailable or stale observations have a separate telemetry alert. Backup age measures the oldest file shipment timestamp, with a twenty-four-hour threshold; the existing backup-lag rule remains independent.

The `host-storage` scrape also collects `ts_orch_edge_responses_total{protocol,code}` with discovery's `host` and `region` labels. Its sample limit covers both HTTP listeners' bounded three-digit status codes plus host metrics. Each response is counted when its final status is committed, including local 502/503 errors, HTTP/1 upgrades as 101 and successful extended CONNECT tunnels as 200. Interim 1xx responses do not add another count. Only observed protocol/code pairs are exported; no route, hostname or tenant labels are added. This job collects the counter once per host; no additional scrape is needed.

To count edge 502s during a five-minute release window, evaluate at the window's end:

```promql
sum by (region) (increase(ts_orch_edge_responses_total{code="502"}[5m]))
```

Use `sum by (host, region)` to locate affected hosts. `increase` adjusts for process counter resets and extrapolates between scrapes; a new series needs at least two samples, so the first observed failures may not be counted in the window.

Deploy the dashboard emitter release and this orchestrator release before installing the updated Prometheus configuration. Dashboard app-listener metrics require loopback peers, literal loopback Hosts and absent forwarding headers; public proxy requests must remain 404. Existing TerraBase/auth histogram counts are normalized by recording rules; see [the HTTP coverage limits](../slo.md). Confirm `up{job="application-slo"} == 1`, both outcomes of `terrascale_slo_requests_total` for every serving process, and a distinct instance during overlap. After an eligible request, verify `slo:requests:rate5m` and the absence of `ServiceSLOTelemetryMissing`. A successful scrape alone cannot prove native SLO coverage. The relay at `127.0.0.1:9094/metrics` separately emits the three fixed service-readiness series; those probes supply no request successes.

The four `ServiceSLOBurn*` alerts retain their paired-window burn thresholds and
require at least 695 requests in 1h, 1,667 in 6h, 3,334 in 1d or 10,000 in 3d,
respectively. These minimums require more than ten estimated bad requests at the
threshold; see [the arithmetic and cancellation policy](../slo.md#burn-rate-alerts).
Dashboard visitor disconnects must increment neither native outcome counter.
The dashboard emitter correction ships separately in `terrascale`; updating
these rules alone does not correct already misclassified cancellations.
`ServiceReadinessFailed` retains its independent public probes and five-minute
hold even below these request minimums. Missing request counters still produce
`ServiceSLOTelemetryMissing`; scrapeable counters with no traffic do not prove
availability.

Operational alerts use existing backup/replication metric names. Failed daily restore drills use the existing `terrabase_backup_drills_total{result="failed"}` counter. Missing operational series cannot prove backup health. Counter rules use a five-minute increase plus first-observation detection: an existing nonzero value fires when collection starts, then ages out after five minutes without another failure. This also detects counter resets followed by failures. `TerraBaseMetricsDown` and `TerraBaseHostMetricsDown` require two minutes of failed scrapes before firing.

Alertmanager sends critical firing and resolved webhooks to `http://127.0.0.1:9094/alerts`. Critical firing groups email and push at once; resolved groups only push, since recovery needs no action. Warnings (SLO slow burns, missing telemetry, storage warnings) go to `/alerts/digest` as one group without resolved notices: at most one digest email per 24 hours and never a push. Readiness must fail for five minutes and recover for ten before the alert changes state, so probe flaps do not page. The installer manages the relay alongside Prometheus and Alertmanager and checks its `/healthz`; this proves listener readiness and usable credential files, not external delivery. No installation, activation or live delivery proof is claimed here. A controlled firing alert and its resolution still need verification against the deployed release, provider responses and the owner's actual inbox/phone receipt.

The relay is the single binary's `ts-orch alert-delivery` command. It binds only `127.0.0.1:9094`, reads the two existing Cloudflare refs and its private topic from root-prepared credential files on each delivery, and emails mariogk@terrascale.tech. The user approved sharing exactly `gru-1-cloudflare-account-id` and `gru-1-cloudflare-email-token` with ts-alerts. The only additional owned ref is `gru-1-ts-alerts-ntfy-topic`; no new IAM permissions are authorized by this runbook.

The unit runs `alert-delivery prepare` as root before starting the relay. It reads the three approved references from SharedVault using instance principal and writes root-owned, group-readable files under `/run/ts-alert-delivery` on tmpfs with swap disabled. The unprivileged relay reads those files without metadata access. A relay restart refreshes all three files. Follow the [checked release order](../../../docs/releases.md#service-credential-releases): release the updater alone before installing the unit, verify the file-reading relay and real delivery before applying metadata restrictions or removing an existing relay exception. Preserve existing protections and that exception until verification succeeds; restore the exception after a failed check. Push reads the private, randomly generated `gru-1-ts-alerts-ntfy-topic` from its file, independently of the two email reads. Provision the topic through an authorized administrative operation; runtime never creates secrets or changes IAM. Topic knowledge grants publish and subscribe access: keep it private and treat pushes as prompts to inspect trusted monitoring/email. Push sends generic status only. Subscribe from a host running the updated release:

```sh
ssh -t ts-gru-1 'sudo -u ts-alerts /usr/local/bin/ts-orch alert-delivery subscribe'
```

This command requires a TTY, displays the topic/link only on that terminal, waits for Enter after subscription, then sends one generic test through the loopback relay. Do not record or share its terminal output.

Email and push are independent: accepted or queued email returns HTTP 202 even if push fails; push failures are logged without provider details. Email attempts are capped at 12 per rolling hour across all groups and statuses (at most 288 per 24 hours), reserving the rest of the shared 1000/day quota for sign-in. Each group/status is suppressed for four hours, matching `repeat_interval`, and every digest shares one 24-hour slot, regardless of changed fingerprints within that group. Older payloads without `groupKey` use sorted fingerprints or labels.

Reservations are written before sending to `/var/lib/ts-alerts/email-ledger.json`, with file locking and atomic, synced replacement. `StateDirectory=ts-alerts` preserves the budget across restarts. Apply the updated unit with the release; without a writable ledger, email fails closed. Windows expire from the request deadline (up to 50 seconds after reservation) to cover locking, Vault reads and delayed sends. Failed or ambiguous email attempts consume a reservation too, so a lost provider response cannot cause a duplicate. Duplicates, capped attempts and ledger failures return HTTP 202, log the suppression and still attempt push. Do not delete the ledger to recover delivery. HTTP 202 means the webhook was handled, including email suppression; it does not prove inbox/phone receipt.

`TerraBaseBackupLag` holds for `2m` and `TerraBaseReplicationSendLag` for `5m`. With 15-second scrape and evaluation intervals plus the 30-second initial `group_wait`, a newly observed sustained lag has a nominal initial notification budget of about 3 and 6 minutes (15s scrape + 15s evaluation + hold + 30s grouping). An alert that joins an existing group waits for its five-minute `group_interval`. This is configuration timing, not measured end-to-end delivery; provider latency, retries and outages can extend it.

Missing native request counters produce telemetry warnings instead of measured availability. A failure of ts-gru-1 stops scraping, evaluation and delivery together. Independent host-failure detection and actual recipient receipt remain unproven.

The relay probes only fixed public HTTPS endpoints: `https://api.terrascale.tech/readyz`, `https://auth.terrascale.tech/readyz`, and `https://dash.terrascale.tech/readyz`. Each scrape runs the three probes concurrently with verified TLS, no environment proxy, no credentials, no redirects, a three-second timeout per probe and a 16 KiB response limit. API/auth require HTTP 200 JSON with `status=ready`; dashboard requires HTTP 200 JSON with `status=ok` and both `dependencies.ts-auth=ok` and `dependencies.terrabase=ok`. Timeout, TLS failure, non-200 or invalid expected JSON yields zero. Only fixed service labels are exposed; errors and URLs are never metric labels. Caller-selected targets are not supported.

`ServiceReadinessFailed` pages critically for any of the three services after five minutes of sustained readiness failure and resolves after ten minutes of recovery. With 15-second scrape/evaluation intervals, at most three seconds probing, the five-minute hold and the initial 30-second grouping wait, the first notification goes out five and a half to six and a half minutes after readiness fails. Existing groups, retries and provider delay can extend delivery. Readiness is a public endpoint check, not a full user operation or fleet SLO. These gauges manufacture no request successes; native SLO counters are collected separately. Relay/host failure can remove readiness samples altogether; this rule alone does not detect missing series.

The relay observes executed production journeys independently of scrapes every thirty minutes, with a thirty-five-second total deadline and three seconds per API call. A refresh makes at most eleven unauthenticated GitHub API calls (one runs listing and at most ten job listings), at most twenty-two per hour across relay restarts. The next refresh time is reserved durably before API access, using the same locked, atomic state-file pattern as the email ledger. Last-good results and observation timestamps are persisted in `/var/lib/ts-alerts/journey.json`. An unreadable or malformed file never prevents the alert endpoint opening: the observation is unknown (`observed=0`), missing telemetry warns, no journey API requests are made, and one line is logged until recovery. The file is checked each minute while malformed; repairing or replacing it restores observation subject to its durable reservation. Reservation or state errors prevent API access. It preserves the last successful observation on lookup errors and exports its age; missing telemetry warns after the observation is over sixty-five minutes old for ten minutes, or the completed journey is over thirty-six hours old. A restart inside a reserved interval makes no API calls; the first start without state allows one refresh. Lookup errors retain the last good observation and its reserved schedule. Provider refusals extend that reservation to the latest of the thirty-minute interval, `Retry-After` (seconds or HTTP date) and `X-RateLimit-Reset`.

Backup age applies only to members with a positive last-success timestamp. A member that has never shipped files does not trigger this age rule. Database scrape failures use their dedicated alert; other application targets use the generic alert. Kernel OOM kills warn on any increase over fifteen minutes and identify the host.


The production journey gauges describe the **production journey's last result from GitHub**. They do not attest to alert delivery.

`AlertDeliveryHeartbeat` always fires with `delivery_probe=heartbeat`. Alertmanager routes it through the normal local relay receiver every five minutes, in its own group, with no initial group wait. The relay removes probe-labelled alerts before real notification handling and sends them to a bounded background worker. For this label alone, it publishes a random nonce to ntfy, then polls ntfy's cached-message API and verifies the same message ID, topic and nonce. Completion is persisted atomically to `delivery-probe.json` and exported as `terrascale_alert_delivery_probe_completed_timestamp_seconds`; zero means no trustworthy completion. A scrape does not initiate a probe.

The probe topic is `ts-probe-` plus the unpadded base64url HMAC-SHA256 of the fixed label `terrascale-alert-delivery-probe-v1`, keyed by the real push-topic secret: 52 characters from the push service's topic alphabet, inside its 64-character limit. It uses the same secret reader and push service as real push. Knowledge of a topic is this push service's credential. The derived topic has no human subscribers, is never shown by the subscription command, is not guessable without the real secret, and is explicitly checked against the real topic before publication. Probes never publish to the real topic, send email, or notify a person. They never fail real alert deliveries and never use a real delivery's handler; a probe that starts first can hold the shared credential provider for its own bounded request, at most 12 seconds.

A durable locked reservation permits at most one attempt per five minutes across restarts: at most 12 Vault topic reads and 24 push API requests per hour (one publish and one read-back per attempt), with a twelve-second total attempt deadline and 64 KiB response bounds. No retries are made; failed attempts consume their reservation. Invalid probe state reports no trustworthy completion and suppresses probe requests until repaired. Successful completions older than fifteen minutes page critically without an additional hold; zero or absent completion telemetry holds fifteen minutes before paging.

This probe proves rule evaluation → Alertmanager routing → relay → push publish → push API read-back. It does not prove email or actual phone/inbox receipt, recipient subscription, public app behavior, or availability of the monitoring host from outside. Its stale/missing alerts travel through the normal path: if that path is broken, these alerts cannot arrive either. An external heartbeat watching the monitoring host is a separate later change; this completion metric is what it will read.

The rule lane models a normal task restart as 40 seconds down, including the one-replica auth service briefly at 0 of 1. Both two-minute scrape holds and the five-minute coverage hold exceed this modeled interval, and the evaluator verifies they remain silent. Forty seconds is the lane's restart scenario, not a measured production restart promise. A rollout that exceeds a hold can page and should be investigated. The runtime lane seeds the real agent assignment database, uses actual containerd tasks and the real exporter, kills the assigned dashboard process without a task manager to restart it, and requires expected=1, running=0, discovered=0. It also runs the real relay binary with malformed journey state inside isolated mount/network namespaces.
