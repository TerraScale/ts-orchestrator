# Existing gru host monitoring (TS-820)

1. Validate without installing: `nice -n 19 deploy/observability/production/install.sh --check`.
2. Deploy the monitoring backend to the existing host: `deploy/observability/production/install.sh ts-gru-1`.
3. On that host, inspect `systemctl status ts-prometheus ts-alertmanager ts-alert-delivery` and query `curl -fsS http://127.0.0.1:9090/api/v1/targets`.

The SSH host argument must resolve through existing trusted SSH configuration. The host needs systemd, sudo, curl, tar, sha256sum, useradd, timeout, grep and outbound HTTPS. `/usr/local/bin/ts-orch` must already be a release supporting `alert-delivery`. No host, IAM, credentials or paid capacity is provisioned. Installation has not been run against production. The installer creates the dedicated ts-prometheus, ts-alertmanager and ts-alerts users if absent and installs/enables/starts all three systemd units; unchanged reruns start them without restart. Existing data directories are retained. Validation downloads official binaries into a unique temporary directory and deletes only that directory.

Prometheus 3.15.0 and Alertmanager 0.34.1 are pinned with SHA256 hashes from their official GitHub release `sha256sums.txt` files (retrieved 2026-10-23); 0.34.1 was the official latest stable Alertmanager release at discovery. Both amd64 and arm64 are supported. Before installed state changes, the installer checks bounded global help for `alert-delivery` and requires its `--help` usage error (exit 1), never invoking the bare daemon as a probe. The pinned tools validate all configs and rules before installation changes any host files. `--check` validates configs locally without probing an installed ts-orch. Configs live under `/etc/ts-monitoring`; systemd uses dedicated unprivileged users and state directories. All three HTTP listeners bind loopback; Alertmanager clustering is disabled. No secrets are in these files.

Prometheus retains 35 days of data. Disk consumption depends on real series cardinality: check available space before activation and measure actual growth. The reported 21 GiB spare memory is not a measured monitoring memory budget. This is a single-node backend on ts-gru-1, not an independent availability monitor: host failure also stops its alert delivery.

TerraBase native metrics at `127.0.0.1:9091/metrics` are scraped with `region=gru` and `service=terrabase`. The relay at `127.0.0.1:9094/metrics` is also scraped with `region=gru`; it emits `terrascale_service_readiness{service="terrabase|ts-auth|ts-dashboard"}` as three separate fixed service series (one service value per series). The original `../slo-rules.yml` is installed unchanged, including its missing-telemetry alerts for all five policy services. ts-auth and ts-dashboard metrics ports are dynamic and deliberately not guessed. No request SLO success or burn-rate evidence is inferred from `up`; absent request counters produce policy telemetry warnings. ts-atlas/ts-router telemetry is likewise not configured here.

Operational alerts use existing backup/replication metric names. Failed daily restore drills use the existing `terrabase_backup_drills_total{result="failed"}` counter. Missing operational series cannot prove backup health. Counter rules use a five-minute increase plus first-observation detection: an existing nonzero value fires when collection starts, then ages out after five minutes without another failure. This also detects counter resets followed by failures. A failed scrape alerts immediately on the next evaluation.

Alertmanager sends firing and resolved webhooks to `http://127.0.0.1:9094/alerts`. The installer manages the relay alongside Prometheus and Alertmanager and checks its `/healthz`; this proves listener readiness only. No installation, activation or live delivery proof is claimed here. A controlled firing alert and its resolution still need verification against the deployed release, provider responses and the owner's actual inbox/phone receipt.

The relay is the single binary's `ts-orch alert-delivery` command. It binds only `127.0.0.1:9094`, reads the two existing Cloudflare refs and its private topic via OCI instance principal on each delivery, and emails mariogk@terrascale.tech. The user approved sharing exactly `gru-1-cloudflare-account-id` and `gru-1-cloudflare-email-token` with ts-alerts. The only additional owned ref is `gru-1-ts-alerts-ntfy-topic`; no new IAM permissions are authorized by this runbook.

Push reads the private, randomly generated `gru-1-ts-alerts-ntfy-topic` in the same SharedVault using instance principal, independently of the two email reads. The topic was provisioned once using existing admin permissions; runtime never creates secrets or changes IAM. Topic knowledge grants publish and subscribe access: keep it private and treat pushes as prompts to inspect trusted monitoring/email. Push sends generic status only. Subscribe from delta after the updated release is installed:

```sh
ssh -t ts-gru-1 'sudo -u ts-alerts /usr/local/bin/ts-orch alert-delivery subscribe'
```

This command requires a TTY, displays the topic/link only on that terminal, waits for Enter after subscription, then sends one generic test through the loopback relay. Do not record or share its terminal output.

Both channels are attempted independently, including when credentials or one provider fail. Alertmanager retries incomplete relay requests; partial acceptance can produce duplicates. HTTP 202 and accepted journal events mean provider acceptance, not actual email/phone receipt. Readiness and a successful provider response cannot establish notification latency or delivery to a human.

Both lag rules hold for `2m`; fixtures assert four other firing alerts at `1m45s` and all six at `2m`. With 15-second scrape and evaluation intervals plus the 30-second initial `group_wait`, a newly observed sustained lag has a nominal initial notification budget of at most 3 minutes (15s scrape + 15s evaluation + 2m hold + 30s grouping), below five minutes. Existing groups use a 30-second group interval too, so they do not add a five-minute delay. This is configuration timing, not measured end-to-end delivery; provider latency, retries, existing groups' 30-second `group_interval` and outages can extend it.

Request-based ts-auth/ts-dashboard SLO metrics remain missing, as do their native metrics scrape targets; missing-telemetry alerts disclose the gap instead of claiming measured availability. A failure of ts-gru-1 stops scraping, evaluation and delivery together. Independent host-failure detection and actual recipient receipt remain unproven.

The relay probes only fixed public HTTPS endpoints: `https://api.terrascale.tech/readyz`, `https://auth.terrascale.tech/readyz`, and `https://dash.terrascale.tech/readyz`. Each scrape runs the three probes concurrently with verified TLS, no environment proxy, no credentials, no redirects, a three-second timeout per probe and a 16 KiB response limit. API/auth require HTTP 200 JSON with `status=ready`; dashboard requires HTTP 200 JSON with `status=ok` and both `dependencies.ts-auth=ok` and `dependencies.terrabase=ok`. Timeout, TLS failure, non-200 or invalid expected JSON yields zero. Only fixed service labels are exposed; errors and URLs are never metric labels. Caller-selected targets are not supported.

`ServiceReadinessFailed` pages critically for any of the three services after one minute of sustained readiness failure; fixtures cover the pending interval, all three firing and recovery, while absent readiness series leave the original operational fixture counts unchanged. With 15-second scrape/evaluation intervals, at most three seconds probing and the initial 30-second grouping wait, the nominal initial notification budget is under two minutes, within five minutes. Existing groups, retries and provider delay can extend delivery. Readiness is a public endpoint check, not a full user operation or fleet SLO. Native normalized request SLO counters remain absent: these gauges manufacture no request successes and make no native instrumentation claim. Relay/host failure can remove readiness samples altogether; this rule alone does not detect missing series.
