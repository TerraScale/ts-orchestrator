# Host disk and IO history

FR1 owns installation: deploy the merged orchestrator release on all three hosts, then run `install.sh ts-gru-1` from this directory. Deploy the TerraBase anchor-timeout metric release before enabling the new backend rules. Never delete Prometheus data or the relay email ledger. The collector starts with the host runtime and binds only the automatically detected NetBird IPv4 on 9108 (free on all three hosts on 2026-10-26); no new credentials, paid services or configuration switches. Peer topology uses main’s loopback 9097 listener from PR #170; 9095 is NetBird server health.

Root runtime discovers hosts/regions from NetBird membership (including disconnected peers and every same-region worker) every five seconds and atomically publishes `/run/ts-orch-observability/storage.json`. Missed pings do not remove targets. Names supply the existing region token; non-region developer peers are excluded. Labels are host/region/service/instance, two fixed filesystem roles, two PSI scopes and read/write for at most 32 whole block devices; partitions and loop devices are excluded. Native scrapes keep only three storage queue gauges and the zero-initialized anchor-timeout counter. No tenant, database, path, process or release labels enter this history. Filesystem roles can share a device: never sum their capacity.

Raw disk counters use kernel sectors ×512 and milliseconds /1000. `host:disk_latency_seconds:rate5m` is mean completion time by direction, throughput is bytes/second, weighted time rate is mean device queue depth. Idle disks yield zero latency. PSI ratios use the kernel's 10-second average. Collector/read failures return HTTP 503, never fabricated zeroes.

Evidence: delta `.cos/briefs/orch-20261021/drills/b8-auth-unavailable.md` records starvation at 60–64% PSI, the rollout below-50% gate, and failures at 93–99%, including an anchor timeout with 18 GB still free. Warning PSI >50% and critical >90% follow that evidence. The 2-minute warning/1-minute critical holds, free-space warning <15% or 5 GiB / critical <8% or 2 GiB, and mean disk latency warning >100 ms / critical >500 ms are conservative initial operating policy, not measured SLOs. Any queued native storage work sustained two minutes warns; a new anchor timeout is critical. Calibrate against retained history without exposing knobs.

All pressure signals aggregate to one alert per host/severity; critical inhibits warning for that host. The child route groups hosts by severity, sending firing and recovery through the existing relay. Separate severity keys preserve warning-to-critical email escalation. Alertmanager forwards at most 64 alert details; the relay explicitly includes the exact additional-alert count and directs operators to Prometheus for every affected host. This preserves a bounded notification through fleet changes; history is never truncated. Its four-hour suppression and shared email cap remain in force. Host failure still shares GRU's backend failure domain.

After FR1 installs, verify both storage scrape jobs are up for every admitted host and query the raw series plus `host:disk_latency_seconds:rate5m`, `host:disk_throughput_bytes:rate5m`, `host:disk_queue_depth:rate5m`, `terrabase_storage_queued`, and `terrabase_catalog_anchor_timeouts_total` in Prometheus `/graph`. Observe at least two scrapes before rate queries. Send one synthetic host-storage group through Alertmanager, resolve it, and verify receiver/provider evidence; HTTP 202 alone is insufficient. Never induce low disk or IO saturation on production. Rule fixtures cover bounded low-space/PSI input, coalescing, recovery, timeout/reset and healthy zeroes; physical fault injection belongs to an isolated cell.

Retention remains 35 days. COS owns the pending seven-continuous-day check: for each host, query `count_over_time(ts_host_io_psi_ratio{scope="some"}[7d])`, verify expected 15-second sample coverage and no gaps using range queries, and check oldest retained samples for disk/queue/anchor series. Configuration alone is not seven-day evidence. Record activation time and actual backend disk growth; do not truncate retention to mask disk pressure.
